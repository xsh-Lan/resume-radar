# 逐句审阅与全文定稿

读取 `<plugin-root>/standards/diagnosis.md`。没有岗位判断时先进入本插件 `skills/resume-radar/SKILL.md` 的模式选择；用户只要求局部文字编辑时尊重范围，可直接完成局部审阅并披露未做完整岗位诊断。

## 审阅顺序

1. 先判断每段经历对目标岗位承担什么主张，哪些事实最有说服力、哪些重复或弱相关。
2. 覆盖每个原文单元，按事实、能力、岗位价值、表达四层检查。父级经历保留上下文；一条 bullet 中不同子主张分别说明，涉及因果或跨句合并时给完整段落。
3. 指定 keep/rewrite/merge/compress/drop/needs_input。好句保留并简述原因；客观字段做一致性检查。修改必须有明确问题或目标依据，不要求每句替换或凑固定问题数量。
4. 复用上游诊断 ID；reason 仅说明本句的编辑动作与取舍，完整岗位差距保留在内部统一诊断中；每条审阅的question只问当前原句，不能直接复制涉及另一项目的全局问题。新发现的根因补充到共享诊断后再引用。未关联诊断的局部表达问题直接说明修订理由。材料不足时给忠于已知事实的保守版本，将待确认问题放在正文之外。drop 是目标版本建议，保留来源档案。
5. 默认只突出影响岗位判断的修改，好句汇总保留；内部完整审阅不等于展示全部推理。用户要求完整逐句审阅时展示所有单元。局部调用只审约定范围，不因没有 JD 而强制转入主入口或等待全量诊断。用户请求改写时交付完整目标版本，检查所有权、时间、数字、完成状态与全文一致性。

## 写作判断

完整改写必须读取本插件 `skills/excellent-resume-patterns/references/writing_system.md`，先以一段经历为单位重建叙事，再回到逐句审阅。不能用逐句删词代替经历分析。

1. 对每段核心经历找出：面向谁的什么问题、本人承担的任务、实际动作与选择、已交付或已测得的结果。每个判断回指原句；没有写出的环节标未知，不补故事。
2. 选最能支撑目标岗位的一条主线。例如产品岗优先呈现问题识别、方案取舍、验证与协同，技术名词用于解释方案；开发完成或测试数量不能自动证明用户价值。
3. 核心经历优先采用“【具体工作主题】压缩的STAR叙述”：背景和任务简短交代，主要篇幅写本人动作、方法、选择与结果。不要逐条打印S/T/A/R标签，不要求每句凑齐四项。标题必须来自该句事实，不使用“业务赋能”等空标题。客观字段、栏目和简单信息不套用此结构。
4. 数字先判断作用：工作量、覆盖范围、过程质量或业务结果。保留有意义的原始规模与明确交付；测量口径未清的结果给保守稿，并说明核实后如何放回，不能把删掉所有结果当作优化。
5. 原因与建议解释本句的岗位价值、原表达为何遮蔽价值、此次如何重排或取舍；必要时指出从任务执行到产品判断还缺哪条事实。避免每句只写“更简洁”“待核实”。同一经历跨句分析后，理由仍严格对应当前原句。

交付前比较原稿和改稿：读者能否更快看出本人解决了什么、怎么做、交付到哪一步？如果只缩短了字数或增加了标题，继续修订。STAR是组织真实事实的方法，不能把“参与”改成“主导”，也不能把交付改成效果。

从真实动作、对象、方法、决策或产物出发。原文的参与、协助、独立完成分别保留；贡献升级须有明确补充来源。缺结果可写真实交付与阶段，不引入效率或增长结论。句长、拆合、信息顺序服从阅读和岗位价值，不硬性要求一行或每条数字。

示例使用同一组事实：已知“访谈8名商家；发现入口难找；整理问题并画原型；提交负责人；尚未上线”。可写“访谈8名商家，识别优惠配置入口难找的问题；整理问题清单并绘制调整原型，提交负责人评审。”它支持访谈、问题归纳和原型交付；上线效果仍未知。

按需读取 `skills/excellent-resume-patterns/SKILL.md` 的条件卡片。排版导出使用当前环境可用的文档/PDF能力，按目标市场、职级和用户要求处理；不得从未渲染的文本推断实际字体、页数或 ATS 解析已通过。

HTML呈现每条只使用一个折叠，展开内容严格为原文、改后、原因与建议。将本句的编辑理由、必要事实问题直接写进原因与建议，不新增查看依据或处理说明等二级折叠。

个人信息同样逐项审阅：姓名字形、电话和国家码、邮箱格式及mailto目标、微信说明、教育与经历日期、作品链接。不要预先脱敏；显示内容与实际链接目标分开检查，事实冲突需指出而不擅自选择。
