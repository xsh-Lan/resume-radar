# 真实岗位发现与检索

适用：无 JD 的完整评估；已有用户 JD 则直接使用，除非用户要求扩展比较。用户明确仅要文字润色或拒绝联网时跳过检索并说明范围。

## 检索与停止条件

先从简历的实际动作、产物、贡献深度提炼候选方向，分别写支持事实、未知、迁移难度和约束。岗位检索使用岗位、地点、职级与通用任务关键词；姓名和联系方式作为简历审阅内容，不作为岗位检索关键词。

首轮选择证据最强的 2–3 个方向，每方向以 3–5 条去重 JD 为检索起点。优先公司官方招聘页面，其次可读取全文的公开招聘平台。岗位阶段与地域尽量一致，适当覆盖不同公司与任务变体。这个数量是探索预算，不代表统计样本。用户指定范围时按其要求调整。

搜索结果标题或摘要只是线索，必须打开并实际读取岗位正文才登记为 JD。记录原链接、公司、职位名称、方向、地点、职级、发布时间或 unknown、读取时间、开放/关闭/未知状态。页面可打开不等于职位仍有效；关闭和日期不明样本可以解释历史任务，明确排除当前在招判断。同一职位跨链接转载时按公司、名称、地点与正文合并，保留一个主来源；同 URL 不重复入库。

满足本轮覆盖且没有新增关键任务差异时停止。方向样本不足时换一次关键词或来源，再仍不足则交付 partial/failed，说明尝试、样本短缺及下一步；不无限绕过访问限制或填造岗位。浏览工具不可用时明确写出工具缺失与未执行查询，在 attempts 中记录 planned_query 和 query 的意图差异：未执行的 query 填“未执行：工具不可用”，outcome 写明原因，不虚构已搜索。只有所有计划方向都达到本轮覆盖才记 complete；数量和状态不证明语义代表性。

## 交接与比较

使用 `workflow.py add-jd` 保存已读取正文及元数据。招聘来源 kind=jd_sample，不能放进候选人 evidence；要求 basis=sample_jd，source_unit_ids 指向对应岗位正文。每个来源只关联自己的候选方向。检索样本的硬条件只适用于该具体 JD，不能升级为整个方向的门槛。共性使用“本次 n 条样本中 x 条提及”并引用实际来源；单家公司要求单列。

`run.market_search` 保存状态、尝试、局限；`role_options` 引用候选人证据及 JD 来源。没有 JD 的方向披露 search_limitation，允许继续基于明确标注的 role_standard/hypothesis 做条件分析。

每方向展示：支持依据、真实 JD 链接、样本反复出现的任务与公司差异、direct/transferable/partial/unknown 的材料支持、优先差距、迁移难度与下一步。用户只探索时到此可完成，无需强制完成某个方向的全文定稿。

三项分别解释：简历证据支持度、检索样本中的岗位情况、实际录用结果。少量便利样本不支持市场总量、热度、竞争、供需、趋势或录用概率。搜索失败不意味着该方向没有岗位。
